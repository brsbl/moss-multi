# Suggestions: design review (T5.0)

This resolves ARCHITECTURE §13 "Suggestions" and spike SP11 for M5. It says what a suggestion is in the shared doc, which edits a suggester's client may send, how the DocDO vets them, how suggestions are painted, reviewed, accepted and rejected, and what T5.1–T5.3 build. Where it differs from the A§13 sketch, this document wins, and A§13 now points here.

## 1. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | **Additive edits land; everything else is a proposal.** Typing, pasting, Enter, new list items, table rows and new decorators enter the tree and are registered as the author's parts. Deleting, formatting, retyping or re-indenting original content never touches the tree: the client records a proposal part, painted as an overlay, applied only on accept. | PRODUCT: a violating edit never lands. L§4.12: a suggester's first delete was a real deletion. Proposals keep original content byte-identical until an editor decides. |
| D2 | **Ownership is Yjs identity, not text offsets, item by item.** An insert part is an id set (`{client, clock, len}` spans) of every item the author created, nested ones included. Owning a block does not own what others typed inside it: deleting the block deletes its content too, so that content is judged item by item, and formatting the block or its text map changes the others' text it governs. There is no baseline. | The false-4403 family came from re-diffing flat text (L§4.12); the stale baseline came from snapshotting before sync. Item ids have neither problem: colliding-prefix typing is just new items. |
| D2a | **Identity is carried across every writer's splits and joins.** When any frame (an editor's Enter, bold or Backspace join, another suggester's split, a review, an undo, a restore) deletes characters of an open record, directly or with the block holding them, and re-inserts copies anywhere in the body, the DO maps the old ids to the copies and updates the record in the same transaction. | Lexical re-inserts a split or reformatted run with new ids; without the carry the suggested text would lose its paint, its reject target and its clean-export exclusion, and stay in the doc for good. |
| D2b | **Reject and withdraw remove only the author's own items** (owner-delegated ruling, 2026-10-04; PRODUCT restart ruling 16). A suggested block (paragraph, list item, table row) is removed only when no other author's live content is inside it. Otherwise the block stays as an ordinary block holding the other author's text, and only the suggester's characters inside it are removed. An own text map that governs another author's characters stays too, so their format does not change. The suggester cannot reformat or delete a peer's text inside their own new block (D2). | Removing a container makes Yjs delete everything inside it, so "remove the inserted ids" would delete a peer's words on reject, and withdraw would hand the suggester the very deletion the vetter refuses. |
| D3 | **The DocDO vets each suggest-mode frame on what Yjs actually applies, by one invariant.** The frame is applied to a mirror the DO keeps beside the live doc and judged in the mirror's `afterTransaction`; the client judges its own transactions the same way. The original projection of every touched type must be unchanged (§4). Nothing is decoded or placed separately from Yjs. | Three review rounds found new forged-frame forms each time the vetter enumerated struct shapes (forged GC, tombstones, same-value writes, embeds restyling neighbours, recursive deletes). Judging the applied result covers every struct form at once. |
| D4 | **Splits are allowed and their moved text stays original.** Enter mid-paragraph, a soft break or a differently formatted run mid-word make @lexical/yjs delete the tail and insert a copy. The vetter proves the copy and records it, with the new text map governing it, as `moved`: never the author's to delete or reformat, kept on reject. | Refusing Enter mid-paragraph would refuse ordinary writing. Treating the copy, or its map, as the author's would let reject delete original text or a later frame reformat it. |
| D5 | **Only the DocDO writes `Y.Map('suggestions')`.** Inserts are registered from the vetted frame in the same transaction that applies it; proposals arrive as socket messages the DO validates. | A§13 (only the DO writes the meaning maps). One transaction means a peer never sees unpainted suggested text. |
| D6 | **Structural ops are parts, not refusals** (SP11): checkbox toggle and block type are `attr` parts, list indent is an `indent` part, a table row or column insert is an insert, a row or column delete is a `delete` part, Backspace at a block start is a `join` part. | A§13 allows refusal only after an owner ruling. None is needed. |
| D7 | **A refusal is loud and loses nothing typed after it.** The client runs the same vetter on each of its transactions, against the state before it and the same ownership basis the server uses, and refuses before sending. The one race between them (a review the client has not seen yet) is closed by judging ownership as of what the client acknowledged (§4 rule 6). Anything else the server alone refuses is a bug or a forgery: the client still keeps every unacked change as text it offers back after the rebind (§4 "Refusal path", §5.2). | PRODUCT: never silently dropped. DEF-1 (L§4.12): the client kept rejected text. |
| D8 | **Review lives in moss's chrome:** a Suggestions button in the top bar beside moss's `CommentsMenuButton`, opening glyphdown's suggestion cards in a moss-DS popover, plus a popover from the painted suggestion with Accept and Reject. | Moss lists a note's annotations from a top-bar menu (`CanvasAreaContent.tsx:265`); its right panel is the inert agent panel. Glyphdown's interaction is a list of cards with Accept and Reject. |
| D9 | **Export is the working text.** Pending inserts are exported as written and pending deletes are kept; no markers ever. `?view=clean` drops pending inserts and undoes pending splits. | Glyphdown as-is (its content route's `view=clean`, `do.ts:493`); the CLI's three-way merge needs the working text as its base. |

## 2. Data

`Y.Map('suggestions')` maps a suggestion id to a plain JSON record. The DocDO is its only writer, under origin `server-suggestions`; clients never write it (the SP7 classifier refuses any client frame touching it, for every role), and the map is outside every client undo scope (A§10.8).

```ts
interface SuggestionRecord {
  id: string;                 // minted by the author's client (a group), checked by the DO
  author: string;             // server principal id, never client-supplied
  authorName: string;         // display copy from the connection attachment
  source: 'live' | 'cli';
  note?: string;              // `--suggest -m`
  createdAt: number;          // seconds
  updatedAt: number;
  status: 'open' | 'accepted' | 'rejected' | 'withdrawn';
  resolvedBy?: string;        // principal id, or 'system' for auto-reject
  resolvedAt?: number;
  resolvedRev?: number;       // the DO's review counter when the record left 'open' (§4 rule 6)
  outdated?: number;          // parts skipped on accept by the drift guard
  parts: Part[];
  moved: IdSpan[];            // original text this suggestion's splits moved, with the text maps governing it (D4)
}
type IdSpan = { client: number; clock: number; len: number };
type Part =
  | { id: string; kind: 'insert'; ids: IdSpan[] }
  | { id: string; kind: 'delete'; anchor: TreeAnchor }
  | { id: string; kind: 'format'; anchor: TreeAnchor; set: number; clear: number }
  | { id: string; kind: 'attr'; block: IdRef; key: AttrKey; from: Json; to: Json }
  | { id: string; kind: 'indent'; block: IdRef; by: 1 | -1 }
  | { id: string; kind: 'join'; block: IdRef }
  | { id: string; kind: 'replace'; regId: string; from: string; to: string };
type IdRef = { client: number; clock: number };   // the block's (or decorator's) item: its stable identity in V1
```

- `TreeAnchor` is the comment anchor from T4.0 (two RelativePositions, assoc 0 and −1, plus a W3C quote over the tree projection). Proposals reuse it so re-anchoring, the quote and the drift guard are one implementation.
- `AttrKey` is an allowlist: `__checked`, `__listType`, `blockType` (paragraph, heading level, quote), `__format` on elements (alignment), `__language` (code), `__level` (callout), and image and video alt text and width (T5.1 lists moss's property names). Any other property change of original content is refused loudly (§5.2).
- Record size stays small: consecutive typing extends the last span (`register` in the spike), and a group ends on the glyphdown coalescing rule (30 s or more than one paragraph away; `suggest-session.ts`).
- **Per-doc DO state outside the map** (SQLite, so it survives hibernation): `review_rev`, the counter every status change increments; and `yjs_clients(client_id, principal_id)`, the Yjs client ids each principal has written under (§4 rule 1), recorded for every applied write of any role, so an editor who switches Suggest on keeps writing under their own id. Per connection, the attachment holds `seenRev`, the review counter that connection last acknowledged.

## 3. Operations

"Raw frame" is what the vetter returns if the client sent the editor's own Yjs change; "client sends" is what the suggest-mode client sends instead. The reason in a refused row is the first rule the frame breaks (§4). The census asserts the raw-frame verdict for typing, the colliding prefix, a sentence pasted before itself, Enter at the end and mid-paragraph, a soft break, a formatted run mid-word, a new table row and list item, deleting a character and a word, bolding, a checkbox, a list indent, a code register edit, own content, moved text, a peer's text inside an own block, and an own new code block's register; the other rows follow from the same rules.

| Operation | Raw frame | Client sends | Part | Paint | Accept | Reject or withdraw |
|---|---|---|---|---|---|---|
| Type, paste inline, colliding prefix, sentence before itself | allowed | the frame | `insert` | insert highlight | close | remove the author's ids (`rejectPlan`, D2b) |
| Enter at a block end; new list item; new table row or column; new decorator | allowed | the frame | `insert` (every item of the block, nested ones included) | insert highlight, ¶ marker for a new empty block | close | remove the block when nothing inside it is another author's; otherwise keep it as an ordinary block and remove only the author's items in it (D2b) |
| Enter mid-paragraph; soft break; a differently formatted run mid-word | allowed as a split (`moved` > 0) | the frame | `insert` for the new boundary and text; `moved` on the record | ¶ marker at the break; moved text unpainted | close | remove the author's items and keep the moved text: an inserted block holding moved text and no peer text merges into its previous sibling (the split's undo, carried like any split); an inserted text node of moved text stays and Lexical's normalization rejoins it |
| Delete original text (Backspace, Delete, word or line delete, Cut, typing or pasting over a selection) | refused `delete-original` | a `delete` proposal for the original segments; own segments are deleted for real | `delete` | strike highlight | remove the range if its text still matches (§6.3) | close |
| Backspace at the start of an original block | refused | a `join` proposal | `join` | struck ¶ at the end of the previous block | merge the block into its previous sibling | close |
| Bold, italic, code, link on original text | refused `delete-original` (the split re-inserts with new properties) | a `format` proposal | `format` | dotted underline in the author colour plus a format chip in the popover | apply the format bits to the range | close |
| Toggle an original checkbox; change block type, alignment, code language, callout level, alt text | refused `mutate-original` | an `attr` proposal | `attr` | a marker at the block start | set `key = to` if the value still equals `from` | close |
| Indent or outdent an original list item (Tab) | refused `delete-original` (it moves the item) | an `indent` proposal | `indent` | an indent arrow at the block start | indent or outdent the block | close |
| Delete a table row or column, or a whole block | refused | a `delete` proposal over the block range | `delete` | strike plus a tint on the row, column or block | remove | close |
| Edit an original code, HTML or formula payload, or a chart or sketch register | refused `mutate-original` | a `replace` proposal from the decorator's draft (§5.3) | `replace` | a "Suggested change" chip on the decorator | write the register by minimal diff if it still equals `from` | close |
| Edit, delete or format the author's own pending content, including a new decorator's register | allowed | the frame | updates the same parts | — | — | — |
| Delete text a split of theirs moved, or a peer's text typed inside their own block, including by deleting the whole own block | refused `delete-original` | a `delete` proposal for that text; their own text is deleted for real | `delete` | strike | remove | close |
| Format text a split of theirs moved, or format their own text node or change their own block's type or alignment while it governs moved text or a peer's text | refused `mutate-original` | a `format` or `attr` proposal | `format`, `attr` | as above | as above | close |
| Undo (Cmd+Z) of their own split | allowed as a split: the tail comes back as copies, kept `moved` | the frame | updates the same record | — | — | — |
| Title, properties (frontmatter), comments map, suggestions map | refused `outside-body` | nothing: the title and Properties are read-only in suggest mode | — | — | — | — |

Move by drag (an original block dragged elsewhere) is a copy plus a delete: the client inserts a copy at the destination (an insert) and proposes deleting the source, in one record that the review card labels "Moved". Accept removes the source; reject removes the copy.

## 4. Server vetting (SP11)

**Where it runs.** In `DocDO.onMessage` step 4 (A§5.1), beside the cap check, for every write from a connection whose attachment says suggest mode: always for `suggester`, and for an editor or owner who switched Suggest on (§5.1). Inert frames are never vetted.

**How it judges.** The DO keeps a `SuggestMirror` beside the live doc: a second Y.Doc that follows every update the live doc applies. A suggest-mode frame is applied to the mirror first, and `vet` runs in the mirror's `afterTransaction`, where the frame's structs are integrated and its deletes marked but nothing is collected yet. So the vetter reads the state before the frame (items whose clock is below `beforeState`, live unless deleted before this transaction) and after it (the doc as it now stands) from one store, and judges exactly what Yjs did: its conflict ordering, implicit deletes of replaced map values, recursive deletes of deleted containers, and the full delete set, whatever struct forms produced them. The client runs the same function, `vetTransaction`, in its own `afterTransaction` (§5.2). Inputs: `own` and `moved` from `ownSpans(records, author, {seenRev, now})` (rule 7), and `clients`, the principal's rows in `yjs_clients`.

**The invariant.** For every type the transaction touched (`transaction.changed`, plus the parent of every item in its delete set, nested deletes included), the **original projection** before and after must be identical. The original projection is everything in the type that is not the author's live pending insert: every character with its effective format (the values of the text map governing it), every embed by identity, and every map value. The only allowed differences are:

- new items the author's bound client ids created, where suggesting is allowed (anywhere in a body sequence; a new key in `registers`; inside the author's own register or container);
- deletions of the author's own pending items (in `own`, not in `moved`, or new in this frame);
- **moved text**: an original character deleted as half of a split (Enter mid-paragraph, a soft break, a run formatted mid-word, or undoing one), re-proven by a fresh copy with the same character and format at its place in document order. Copies, and fresh text maps governing them, are returned as `moved` and stay original.

Anything else refuses the whole frame. Concretely:

1. **Nothing parks, and only the author's client ids write.** If Yjs leaves any struct or delete pending after the apply (a clock gap, an origin or parent it cannot resolve), the frame is `unresolvable`: it would land later, unvetted. A client id the doc already held must be in `clients`, or the frame is `foreign-client` (it could take a peer's next clocks, and Yjs would drop the peer's real edits at those clocks as duplicates); the first frame under a new client id claims it. A forged GC over known clocks is clipped by Yjs itself, so only its unseen clocks integrate.
2. **Per-frame cost cap.** More than `VET_LIMITS.structs` (20 000) structs integrated or deleted, or more than `VET_LIMITS.types` (2 000) touched types, is `too-large`, refused before any projection is built.
3. **Where new items may go.** Under `root` anywhere (their effect on original content is judged by rules 4 and 5). Under `registers`, a new key or anything inside an own register; anything inside an original register is `mutate-original`. Under any other root (`title`, `frontmatter`, `comments`, `suggestions`) a write or delete is `outside-body`. A formatting mark (`ContentFormat`) is `mutate-original` (V1 never writes one), and so is any frame touching a type that already holds formatting marks, because Yjs rewrites a remote frame's marks after the transaction, outside the judgement.
4. **Map values** (block attributes, text maps, decorator properties, the `registers` map). For each key the frame changed or deleted on a container that existed before and is still live: a value another author wrote must read the same after the whole frame, compared by value as the live entry once Yjs has ordered the frame's items and applied its full delete set. A same-value rewrite is therefore allowed only if that rewrite is the live value at the end (Lexical re-sets every object-valued property of a node it marks dirty, so inserting beside an original decorator produces such writes); the rewritten item stays original and is not registered. Any other change is `mutate-original` unless the container is the author's own, and then only when it changes no one else's content: an own text map's values are the format of the characters it governs (rule 5 checks them), and an own block whose attributes changed must hold nothing that is not the author's after the frame (moved text or a peer's typing).
5. **The body in document order.** Over the top-level blocks holding any touched type, fresh item or deleted item, every original unit live before must still be live after, in order, with the same format; a deleted original character must be matched by a fresh copy with the same character and format before the next surviving original (moved text); a deleted original embed (a block, list item, row, line break or decorator) is `delete-original`. A character's format is read from the text map governing it after the frame, so a new map placed anywhere in front of original text (beside it, behind new characters, or with no right origin) changes that text's format and refuses, unless its values are identical. Text maps are not units: deleting one is judged only by what it does to the format of the characters after it.

The reason reported is the first rule a frame breaks, in this order: 1, 2, 3, 4, 5, then rule 4's own-block check.

6. **Ownership as the client saw it.** `ownSpans` returns the author's open records, plus records accepted after the review counter the connection last acknowledged (`seenRev`), for at most 30 s after the accept. The client sends `{t:'suggest-seen', rev}` on the doc socket once it has applied a record change, so its later frames are judged on what it knew when it typed them. A frame that deleted or reformatted the author's own text concurrently with an accept is therefore a concurrent edit, as if it had arrived a moment earlier, not a violation; a client that never acknowledges keeps nothing for more than 30 s.

**Identity carry (D2a).** For every frame from any writer, editors included, whose deletes (nested deletes included) intersect an open record's `own` or `moved` ids, the DO runs `carryTransaction` on the same mirror transaction before the live doc applies the frame: the alignment of rule 5, matching by character only (an editor's bold re-inserts the run with new properties), so a join's copies in the previous block are found; each copy, and its governing map, is added to the record. The record update is written in the transaction that applies the frame, so peers never see suggested text unpainted. `serverWrite` (review, restore, push) and undo produce ordinary frames and are carried the same way.

**On a pass** the DO applies the same bytes to the live doc in one transaction with the record write: `super.onMessage` under origin `connection`, then the record upsert extending the connection's current group (D5), the `yjs_clients` claim, and any carry. The mirror sees the live doc's update as a no-op, since it already holds those structs.

**Refusal path, end to end.**
1. *The mirror stays clean.* Yjs cannot un-integrate structs, so a refused frame drops the mirror (`SuggestMirror.reset`); the next frame rebuilds it from the live doc with one `encodeStateAsUpdate` and apply. The live doc never saw the frame. Refusals are rare (a client bug or a forgery) and each closes the connection, so the rebuild runs at most once per refused connection. Measured in CI (the census's cost test): a 1.69 MB doc (3 000 paragraphs) rebuilds in 12 ms, and a typing frame on the warm mirror vets in 1.9 ms (run [37203375738](https://github.com/brsbl/moss-multi/actions/runs/37203375738)).
2. *The connection.* The DO sends `__YPS:{t:'write-refused', reason:'suggest'}` and closes 4409 (the protocol value is the shipped `'suggest'`; A§13's `suggest-policy` is the same thing).
3. *The client keeps what it typed.* The client's self-check runs the same function on the same basis, so the server alone refuses only a client bug or a forged frame. Even then nothing typed is lost: on 4409 the client, before discarding its Y.Doc (A§10.5), exports the markdown of every block holding a change not yet acked, closes the pane to input, rebinds from the server, and compares those blocks with the server's. Any block that differs is offered in the band's refusal notice as "Copy what wasn't saved", which holds until dismissed. Input reopens on the fresh binding, so typing after the rebind lands normally (§5.2 step 5; j16 covers it with a frame the client is made to skip checking).

**Cost.** Typing costs one apply of the frame to the warm mirror plus a walk of the top-level blocks it touched, linear in the frame and those blocks; a frame inside a large table walks the table. The mirror doubles the doc's memory in the DO (at most the 2 MB cap). The struct and type caps bound the walk per frame.

**What the census proves** (49 tests, green): additive edits, colliding-prefix typing and a new paragraph beside an original code block pass and register inserts; the three split shapes pass with a non-empty `moved`; deletes, formatting, checkbox, indent and register edits of original content are refused; own pending text can be retyped, deleted and formatted, and an own node or block that governs only own text can be formatted; moved text can be neither deleted nor reformatted, even inside the author's own new block; a peer's text inside the author's block can be neither deleted (directly, or by deleting the block, forged or through Lexical) nor reformatted through the own text map or block; deleting an own block cannot take the moved text in it; a new code block's register stays editable in later frames; a forged text map that re-formats original text, a forged overwrite of an original register, forged tombstones placed after an original register or block attribute, a forged formatting mark, a forged GC overlapping known clocks with a delete of original text, a clock gap, and a write under another writer's client id are all refused (each forgery test first shows Yjs would apply the damage); title and suggestions-map writes are refused; the client self-check in `afterTransaction` gives the same verdicts, register-origin transactions included; undoing a split through the binding's UndoManager passes both the self-check and the server and keeps the returned tail original; an editor's Enter, bold and Backspace join inside or onto pending suggested text keep it the suggestion's; a delete racing an unseen accept lands, and the same frame is refused once the accept is acknowledged or the grace has passed; opening a doc writes nothing, so a suggester is never refused for loading it; a same-value write that the frame also deletes, or that Yjs orders before the live value while the frame deletes that value, cannot remove an original attribute; a new text map cannot restyle original text through new characters between them or with no right origin; reject and withdraw keep a peer's words typed inside the author's new block, with their format, and remove a wholly own block; frames above the struct or type cap are refused; a refused frame never reaches the mirror the next frame is judged on, and the mirror follows the live doc; and a seeded struct-level fuzz (400 rounds over the census's real frames: retargeted origins and right origins, swapped content kinds, map writes onto random containers, added deletes) checks that whenever the vetter accepts, the original projection of the whole doc, as an independent walk computes it, is unchanged.

## 5. Client

### 5.1 Entering suggest mode

- **Toggle.** "Suggest" sits in moss's floating toolbar beside the formatting controls, reachable by a solo owner with nothing selected (docked at rest); a role-locked `suggester` sees a non-interactive "Suggesting" chip instead (L§1.3). The pane publishes `data-edit-mode=edit|suggest`.
- **Wire.** The mode rides the doc socket: `{t:'suggest-mode', on, group}` as the first message after open and on every toggle; the DO stores `suggest` and `group` in the hibernation-safe attachment. A suggester's attachment is always `suggest: true` whatever it sends. A toggle waits for `data-sync-unacked=0`, so buffered edits are always vetted under the mode they were typed in.
- **Inert while in suggest mode.** Background writers (A§10.10) do not run; the title field and Properties are closed (§3, last row); decorator payload views edit drafts (§5.3).

### 5.2 The suggest seam

One new seam, (e), in the vendored `useYjsCollaboration.tsx`, next to (a)–(d), plus host modules in `apps/web/src/host/suggest/`:

1. **Command routing.** High-priority listeners for the delete family (`KEY_BACKSPACE`, `KEY_DELETE`, `DELETE_CHARACTER`, `DELETE_WORD`, `DELETE_LINE`, `REMOVE_TEXT`, `CUT`, and text or paste over a range), `FORMAT_TEXT`, `FORMAT_ELEMENT`, `INDENT_CONTENT` and `OUTDENT_CONTENT`, and moss's block-type and table row and column actions (T5.1 lists the call sites). Over original content they emit proposals and return `true`; over own content they fall through to Lexical. A collapsed delete moves the caret past the struck text, as glyphdown's `suggest-mode.ts` does.
2. **Attribute conversion.** Before the update listener syncs a suggest-mode update to Yjs, it checks the dirty nodes: an update that only changes allowlisted properties of original nodes (a checkbox click, a language picker) becomes `attr` proposals, the previous editor state is restored under `SKIP_COLLAB_TAG`, and nothing is synced. This covers decorator controls that write node properties directly instead of dispatching a command.
3. **Self-check.** An `afterTransaction` handler runs `vetTransaction(transaction, …)` on every local transaction (`transaction.local`: the binding's, the register writers' `REGISTER_LOCAL_ORIGIN` and `REGISTER_INIT`, and the UndoManager's). The state before the transaction is defined exactly, with no shadow doc: in `afterTransaction` the transaction's structs are integrated and its deletes marked but not yet garbage collected (Yjs collects after the handler), so the vetter reads clocks below `transaction.beforeState` as the doc before, treats items in `transaction.deleteSet` as live before, and reads the doc itself as the state after. This is the same function, on the same kind of transaction, that the server runs on its mirror (§4), so it judges exactly the update the provider is about to send. A violating transaction is not sent: the verdict is keyed by the transaction, and the provider's `update` handler (fired after `afterTransaction` with the same transaction) drops that update. The pane closes to input in the same tick (A§10.3 closed fields), the band says "That change can't be suggested; switch to Edit to make it" (an editor) or "…ask an editor" (a suggester), and the session rebinds from the server once earlier edits are acked. Nothing typed after the refused change is accepted before the rebind.
4. **Ownership on the client.** The client calls `ownSpans` on the records it has applied, with its own review counter as `seenRev`, and adds the clocks this Y.Doc created in suggest mode that are not yet acked (the server registers them as they land). This is the basis the server uses for its frames (§4 rule 6), so the two checks agree.
5. **A refusal only the server sees.** With the same function on the same basis, the server alone refuses only a client bug or a forged frame. Even then nothing typed is lost (§4 "Refusal path"): before discarding its Y.Doc on 4409 (A§10.5), the client closes the pane to input, exports the markdown of every block holding a change not yet acked, rebinds, and compares those blocks with the server's; any block that differs is offered in the band's refusal notice as "Copy what wasn't saved", which holds until dismissed. Input reopens on the fresh binding. j16 covers it with a frame the client is made to skip checking, followed by more typing.

### 5.3 Proposals and decorator drafts

- A proposal is `{t:'suggest', group, part}` on the doc socket. The part carries a client-minted id, so a resend after a reconnect is idempotent. Proposals queue while offline and are flushed after the provider reports `sync`, so they always follow the frames they reference on the same socket.
- The DO validates a proposal (role, group ownership, the anchor resolves inside `root`, the attribute key is allowlisted, `from` equals the current value), computes the quote itself, and writes the record. A refused proposal gets `{t:'suggest-refused', id, reason}` and a band notice; the client drops its pending paint. Nothing was applied locally, so there is no rebind.
- Pending proposals count toward `data-sync-unacked` until their part appears in the map.
- **Decorator drafts.** In suggest mode the register wrapper (A§10.10) hands an original decorator's view a local draft (a detached `Y.Text` or `Y.Map` copy) instead of the shared register. When the view commits (blur or its own Done), the wrapper sends one `replace` proposal. Own new decorators edit their real register.

### 5.4 Undo

Cmd+Z in suggest mode undoes the newer of the last own Yjs edit (the binding's UndoManager, seam (a)) and the last own proposal (withdrawn with `{t:'suggest-withdraw-part', id}`). Undoing a split is allowed: the UndoManager deletes the new block (and, with it, the moved copies inside) and re-inserts the tail as fresh copies in the original block, which the vetter proves like any split and keeps `moved` (the census runs it through the binding's UndoManager, on the client and the server).

## 6. DocDO

### 6.1 Modules

- `packages/sync/src/doc/suggest.ts`: the `SuggestMirror` and vetter (merged with T4.0's classifier), identity carry, `rejectPlan`, `ownSpans`, record writes, group extension, `yjs_clients` claims and proposal validation. Lane-owned for M5 (A§5.1 split). The mirror is created when the doc loads and destroyed with it; it is not persisted.
- `onMessage` step 4 vets suggest-mode writes on the mirror; the placeholder that refuses every suggester write today (`#refused`) is replaced. Step 5 runs the carry, on the mirror transaction, for every write, any role, whose delete set touches an open record. String frames route `suggest-mode`, `suggest`, `suggest-seen` and `suggest-withdraw-part`.

### 6.2 Review RPC and REST

- `POST /api/docs/:id/suggestions/:sid/{accept|reject|withdraw}` reaches `DocDO.reviewSuggestion(principal, sid, action)`. Accept and reject need editor or above (A§8); withdraw needs the record's author at suggester or above, which also lets an editor withdraw their own (fixing L§4.12). A record that is not open answers 200 with its current status (idempotent under concurrent review). Every owner GET of a trashed doc shares the trashed read path (L§4.10).
- The RPC runs one `serverWrite` (A§5.1): it resolves each part through T4.0's anchor mapper to Lexical points on the mirror and applies the outcome with Lexical's own operations (`removeText`, `formatText`, `setChecked`, `setIndent`, a block merge, a register diff), so the result equals what an editor's direct edit would produce. Reject and withdraw remove exactly `rejectPlan(doc, inserts)` (D2b): the author's characters and embeds, and an own block or text map only when nothing live inside it, or governed by it, is someone else's; a kept block becomes an ordinary block. A kept block holding moved text and no peer text is then merged into its previous sibling (the split's undo). The record's status change, a fresh `review_rev` as its `resolvedRev`, and the carry of any other open record the write splits are written in the same transaction. A whole record is accepted or rejected at once, as in glyphdown.

### 6.3 Drift, orphans, notifications

- **Drift guard.** A `delete` or `format` part applies only when its range's text still matches the quote at similarity ≥ 0.8 (glyphdown `FUZZY_ACCEPT_THRESHOLD`); `attr`, `indent`, `join` and `replace` apply only when the current value or structure still matches `from`. Skipped parts are counted in `outdated`, shown as an "outdated" badge, and never applied silently.
- **Orphans.** `onSave` revalidates open records: a part whose items or anchor are all gone (an editor deleted the text; the carry has already followed any copy, so a split never orphans a part) is dropped; a record left with no parts is auto-rejected with `resolvedBy: 'system'` (A§13).
- **Notifications.** When a record is created, the DO writes one `suggestion` notification to the doc's owner, unless the owner is the author (glyphdown's rule, extended to live suggestions per A§13). Recipients are re-checked on read (A§8).

## 7. Paint

Paint is derived and never mutates the tree (L§4.12), on the T4.0 paint layer (CSS Custom Highlights plus geometry, SP10):

- `insert` ids resolve to runs of visible items (a peer's characters typed inside someone's suggestion are not painted as theirs) and paint `::highlight(suggest-insert)`: glyphdown's green background and ink, as moss-DS tokens.
- `delete` and `format` anchors paint `::highlight(suggest-delete)` (strike, glyphdown's red) and `::highlight(suggest-format)` (dotted underline).
- Markers (¶ for a split or a new empty block, struck ¶ for a join, an indent arrow, an attribute dot, a decorator chip) are positioned from range geometry in the pointer-transparent overlay.
- Hover and click find the suggestion under the pointer through the paint layer's hit test and open the suggestion popover (§8). The active suggestion gets an outline highlight, mirrored in the list.
- Moved text is never painted: it is original.

## 9. Converter, export and the CLI

- **Export** (A§12) is the working text (D9). `exportMarkdown({view: 'clean'})` exports a copy of the tree with every open record rejected as in §6.2 (its `rejectPlan` removed, so a peer's words inside a suggested block stay, and its splits rejoined); it backs `?view=clean` and is offered nowhere else in M5. Pending proposals never appear in either view, and nothing marks a suggestion in any `.md`.
- **CLI `--suggest`** (T7.3): the T6.1 reconcile runs on the mirror in suggest mode. Its insertions land as an insert part; every deletion, attribute change or move it would make is emitted as the matching proposal part instead; the result is vetted by the same rules before it applies. Pushed suggestions notify like live ones.
- **History** (M6): records live in the doc, so versions carry them. A restore runs through `serverWrite` and leaves records whose parts no longer resolve to the orphan rule.

## 10. Security

- Authorship always comes from the connection attachment or the REST principal.
- Client frames touching `suggestions` (or `comments`) are refused for every role (SP7). A suggester's frame is judged on what Yjs actually applied to the mirror, by one invariant (§4): the original projection of every touched type is unchanged except for the author's new items, deletions of their own pending items, and proven moved text. The vetter never decodes or places structs itself, so a new struct form cannot slip between the decoder and Yjs: the forged frames the census tries (a text map re-formatting original text directly, behind new characters or with no right origin; a GC overlapping known clocks to hide a delete; a tombstone, formatting mark or same-value write whose integration removes an original value; a delete set naming only an own block that holds others' text; a clock gap; another writer's client id) never land, and a seeded struct-level fuzz over real frames checks the invariant on every frame it accepts.
- Each frame's cost is capped (structs and touched types, §4 rule 2), and a refused frame never stays in the mirror.
- Nothing parks: every struct and delete in a vetted frame integrates now or the frame is refused, so a forged frame cannot wait for a predictable future item. A principal writes only under Yjs client ids it claimed. Claiming a client id that another live connection announces in awareness is also refused (T5.2), so a forger cannot claim a peer's id before the peer's first edit.
- The seen basis (§4 rule 6) widens nothing beyond what a concurrent edit could do: the author changes only text that was theirs within the last 30 s.
- Proposals and reviews are checked against the live role. Withdraw is author-only (L§4.17 SEC-1). Notifications are re-checked on read.

## 13. Risks

- **Coverage of moss's editing surface.** Any moss action that mutates original content and is neither routed nor attribute-only is refused loudly (D7) until it is routed. The T5.1 enumeration test keeps the list honest.
- **@lexical/yjs internals.** The split proof depends on V1 storing a text node as a map embed followed by its characters, and on Lexical keeping the head of a split in the original node; both are pinned by the census at 0.48. A Lexical upgrade re-runs it.
- **Copy matching.** A split's copy is matched character by character with identity preferred, so it cannot steal an original that survived; the only ambiguity (identical adjacent fresh text) does not change the resulting text. The same rule lets a frame replace an original character by an identical fresh one: the text and format are unchanged, but anything anchored to the old item (a comment, a RelativePosition) sees a delete, as it does for an ordinary split.
- **The mirror's memory and rebuild.** The DO holds two copies of the doc (at most twice the 2 MB cap), and a refusal pays one rebuild (§4 "Refusal path"). Vetting on a scratch copy of only the touched state would avoid both, but Yjs integration needs the whole store to resolve origins, so the full mirror is the simpler sound choice. The carry matches by character only, so an editor who deletes a suggested letter and types the same letter in the same frame hands it to the suggestion; the text is identical either way.
- **Moved and peer content is frozen for its author.** After a split, or once a peer has typed inside the author's pending text, the author cannot reformat that text through their own text node or change the type of their own block while it holds it (§3); the client turns both into proposals. Bolding their own text typed at the very start of a moved run makes Lexical write the moved run's map and is refused loudly until T5.1 routes it as a proposal too.
- **Paint in WebKit.** Strike and underline ride ::highlight text decoration; T4.0's SP10 probe covers both engines, and its overlay fallback applies if it fails.

## Owner summary

**What a suggestion is.** When someone suggests, what they add (words, new paragraphs, list items, table rows, images) goes into the note right away, highlighted green, so everyone sees it as they type. What they would remove or change (deleting words, bolding, ticking a checkbox, indenting, deleting a table row) is never done to the note: it is drawn on top as a strike-through or a marker, and only happens if an editor accepts it. Rejecting takes the additions back out and leaves the original exactly as it was.

**Why it is safe this time.** The old attempts compared text before and after, which wrongly refused ordinary typing (typing "the " before "the cat") and once let a suggester's first delete really delete. This design tracks who created each character, using the identity the sync engine already gives every character. A test drove real moss editors through 14 kinds of edits and confirmed:
- ordinary typing, pasting, pressing Enter anywhere (even mid-paragraph) and new rows are accepted;
- every delete, format or checkbox change of someone else's text is caught, even inside the suggester's own new paragraph;
- every hand-made forged edit the reviews found is refused, including ones built to slip past the check;
- undoing your own Enter works, and an editor's Enter, bold or paragraph join never makes a suggestion lose its words;
- opening a note never trips anything.

**What the review changed.** The first draft had holes a reviewer found. The main ones: a forged edit could hide a delete, someone else's Enter inside a suggestion made the suggestion lose track of its own words, and a suggester could lose typing if an editor accepted at the same moment. Each now has a test that failed before the fix and passes after it. A second review found five more holes, all fixed the same way: two kinds of hand-made edits could still remove original content indirectly (the sync engine deletes things the edit never names), a suggester could restyle or delete someone else's words by acting on their own paragraph, an editor joining two paragraphs made a suggestion lose its words, and undoing your own Enter was wrongly refused. A third review found two more hand-made edits that got through, and that rejecting a suggestion could delete someone else's words typed inside it. Since every review had found a new kind of hand-made edit, the check was rebuilt instead of patched again: the server now applies each suggested edit to a private copy of the note and compares what everyone else's content looks like before and after. If anything that is not the suggester's own pending text changed, however the edit was built, it is refused, and the copy is thrown away and rebuilt. A randomized test mangles real edits hundreds of times and confirms the check never lets a change to anyone else's content through.

**Rejecting keeps other people's words.** If someone types inside a paragraph that a suggester added, rejecting or withdrawing the suggestion removes only the suggester's words. The paragraph stays, as an ordinary paragraph holding the other person's text.

**What you will see.** "Suggest" sits in moss's floating toolbar; someone shared as a suggester sees a fixed "Suggesting" chip. A Suggestions button next to moss's comments button lists every open suggestion with Accept and Reject; clicking a highlighted suggestion opens the same card in place. The note's owner gets a bell notification when someone suggests.

**If something cannot be suggested.** If someone tries a change the app does not know how to turn into a suggestion, the app catches it before sending, says so plainly in the notice band, and stops input until it has reloaded the note, so nothing typed afterwards is lost. The server runs the same check as a backstop. If the server ever refuses something the app missed, the app keeps what wasn't saved and offers it back to copy. The test suite lists every moss editing action so that this stays rare.

**Choices made for you** (each can be overturned):
1. The title and note properties cannot be suggested; they stay read-only in Suggest mode.
2. Editing the inside of an existing code block, chart, sketch or HTML block is suggested as one "replace this block" change, shown as a chip, rather than painted character by character.
3. Exports contain the suggested additions as written (the note as it currently reads), with no markers; a "clean" export without pending additions exists for tools.
4. A suggestion is accepted or rejected as a whole, not part by part, as in glyphdown.
5. For 30 seconds after an editor accepts a suggestion, its author can still change those words if their screen had not caught up yet. This is treated as if their change came a moment before the accept.

No owner decision is needed to start M5.
